# 自動化整合契約

本文定義 Airedale、內網 Worker 與 Whippet 的目標契約。標示「規劃」的能力須實作、驗收後才可啟用。流程、分流與驗收見 [自動化需求](../requirements/automation.md)。

## 系統與權威資料

| 系統 | 責任與權威資料 | 連線方向 |
| --- | --- | --- |
| Airedale（DMZ） | 既有回饋單、留言、草稿、認領及客戶狀態。D1 規劃持有工作狀態、租約、審查決策、續辦位置、來源事件、巡檢單對應與寫入收據 | 內網 Worker 向 DMZ 發起 HTTPS 連線。DMZ 提供受限入口與團隊／客戶介面 |
| 內網 Worker | 管理專案範圍、授權、PM／RD 執行、整合游標與外部呼叫，向 Airedale 領件及回報。工作以 D1 紀錄為權威 | 可連 Airedale、範圍內的 Git 平台／ELK、Whippet 與核准的模型入口 |
| Whippet | 測試草稿、驗證執行、QA 發佈、正式測試版本、Run 與執行證據 | Worker 讀取結果、提出測試草稿及請求執行。Whippet 自行派發 Runner |
| Git 平台／部署系統 | 分支、commit、MR、審查與合併由 Git 平台認定。部署系統提供實際部署的環境與版本 | Worker 使用各自的受限身分，查證 MR、訂閱或輪詢部署結果 |

現有 Airedale 可經 API、MCP 或 CLI 讀單、認領、留言和交接，團隊 API 與巡檢 API 支援待審留言。認領供人員協作，工作佇列需要自己的租約。既有巡檢 API 與團隊 API 的權限須另外核對，接到 Worker 後應由專用受限入口執行專案授權。現有 OpenCode 輪詢為增員流程接入的起點。來源事件、機器巡檢單去重、部署重測關聯及專用結案操作均屬規劃。 [專案設定](../../AGENTS.md)、[現有接入說明](../../README.md)

## 專案執行範圍

每個工作使用 `project_slug`、`environment`、`scope_revision` 解析管理者維護的設定。Worker 只接受登錄的專案／環境組合，範圍由設定解析並在實際呼叫前驗證。

| 設定 | 必要資訊與用法 |
| --- | --- |
| 專案和存取 | Airedale 專案 slug、可處理來源、環境代號、各服務身分及祕密參照。自動發單、自動回覆、巡檢自動結案各由專案政策控制 |
| 程式庫 | 穩定 repo ID、核准 remote、基底分支、可讀文件或目錄、允許的工作分支前綴及測試／檢查入口。Worker 以固定基底 commit 建立隔離工作目錄，檢查解析後的路徑是否仍在授權範圍 |
| ELK | 環境對應的 data view／index alias、可查服務、允許的查詢範本及輸出欄位、最大查詢期間和筆數、遮罩規則。唯讀轉接器以受驗證的參數查詢 |
| 部署 | 核准來源、元件與環境對應、可信版本證據，以及可觸發重測的條件 |
| Whippet | workspace ID、允許的測試 ID、巡檢資格、環境、正式版本與檢查識別子的對應，以及可接受的重測版本規則 |

增員流程可從既有 `recruitment-flow` 的 recruitment、agent、staff 及本機說明設定起步。每個 repo 的路徑、remote 與基底分支須由部署者核對。ELK 缺少授權或設定時回報證據缺口。每次工作保存使用的設定版本與選定的 repo／測試版本。設定撤銷即停止後續讀寫，恢復執行時再次核對當前授權。

## 事件與操作

以下名稱為規劃中的邏輯契約。轉接器可先採輪詢，來源可提供事件時再接 webhook。它們共用相同的事件 ID、版本、欄位與去重規則。

### 事件格式

共通欄位為 `schema_version`（首版為 `1`）、`event_id`、`event_type`、`source`、`scope`（`project_slug`、`environment`）、`occurred_at`（UTC）、`correlation_id`（如已指派）、`payload`。以 `(source, event_id)` 及負載雜湊記錄接收結果。來源須經服務身分驗證，轉接器依核准的來源對應解析專案與環境。客戶資料、測試內容與事件負載中的可見性宣告都不能授權。

| `event_type` | `payload` 必要資料 | 接收後處理 |
| --- | --- | --- |
| `report.created`、`report.customer_replied` | `report_public_id`、`report_revision`、回覆事件的 `message_id` | 開啟或恢復工作。開始分析及寫入前重新讀單，核對版本、刪除／結案與認領狀態 |
| `whippet.run_finished` | `workspace_id`、`test_id`、`version_id`、`run_id`、當前 `attempt_id`、Run 的終態、執行用途（例行巡檢／部署重測／草稿驗證） | 讀回 Run 並驗證是否為範圍內執行及目前有效的 attempt。部署重測另依已保存的工作關聯核對 |
| `deployment.succeeded` | `deployment_id`、`component_id`、實際上線的 `artifact_revision`、可驗證的 commit 或建置清單 | 比對實際上線環境、元件、待驗修正或核准用於巡檢的部署對應，建立重測請求 |
| `deployment.failed` | `deployment_id`、`component_id`、錯誤分類 | 記錄部署未成，維持待部署。交由現有部署流程處置 |

Run 事件可附 `check_key`、`failure_kind`、`failure_signature`、`evidence_refs`，以及已建立關聯的 `retest_request_id`。證據只以受權限控管的參照流通。事件未附穩定識別子時，轉接器必須從權威資料取得可驗證的識別子，人工補正前保留待查紀錄。事件時間用於追蹤與查詢，先後判斷以來源序號或權威資料版本為準。

`report_revision` 是單據寫入的版本前提。D1 依建立單據或新增客戶輸入的來源識別決定何時派新工作。團隊草稿、認領、交接或自動化回寫可以更新單據版本或作業紀錄，新版本須在操作收據中回傳供同一工作續辦。

### 操作格式

有寫入效果的操作使用 `operation_id`、`correlation_id`、`project_slug`、`environment`、`scope_revision`、操作種類與必要參數。涉及回饋單時加上 `report_public_id` 與預期 `report_revision`。由 Worker 領件發出的寫入須帶 `work_id` 與 `lease_generation`，以 D1 的現行租約與單據版本核對。回應回傳操作 ID、狀態及權威物件 ID（例如 `report_public_id`、`message_id`、`mr_id` 或 `run_id`）。

| 介面 | 現有入口與規劃的整合行為 |
| --- | --- |
| 收單、認領與交接 | 依既有專案＋`public_id` 操作。規劃補充單據版本與可恢復的事件游標。輪詢重新讀取與處理版本相同的單，由工作索引去重 |
| PM／RD 工作 | PM 派發工作 ID、回饋單識別、業務摘要、證據參照、核准的 scope。RD 回報分流（說明／補資料／bug／需求）、證據與缺口、修正分數及理由、驗證、建議對外文字、分支／commit／MR（如有）。Worker 驗證欄位、授權與實際完成情形再執行下一步 |
| 團隊核准與續辦 | 審查決策綁定 `work_id`、方案版本、回饋輸入版本與 `scope_revision`，由 D1 記錄審查者與決策。續辦前核對方案及輸入仍有效，並重查實際授權。已變更的方案重新送審 |
| 留言及請確認 | 既有留言及 `requestCompletion` 共用服務。規劃用受限操作紀錄操作 ID、防止重送，以及在送出前比對單據版本。自動回覆使用遮罩後的客戶文字，特殊情況可寫團隊待審草稿 |
| 巡檢發單 | 受限操作接收來源 Run、失敗群組與脫敏摘要，原子查找或建立團隊限定單並登記事件及對應；既有開單入口本身無此契約 |
| Whippet 反向連結 | 巡檢發單或合併完成後，依 `(workspace_id, run_id, project_slug, report_public_id)` 寫回工單關聯，Whippet 在具權限的 Run 詳情顯示穩定的 Airedale 工單網址。連結需在 Airedale 獨立驗證登入及單據存取權 |
| 觸發 Whippet 重測 | 接收專案、環境、元件、部署 ID、artifact revision、workspace／test／published version、巡檢單關聯。記錄權威 Run ID 與固定的執行快照。重送必須取得同一 Run 或先查明首次請求結果 |
| 巡檢結案 | 受限操作驗證來源、可見性、專案自動結案政策、單據版本及最新重測證據後，再由 Airedale 更新單據並記錄系統身分。既有客戶結案規則繼續適用於所有客戶單 |
| 測試草稿及發佈 | Whippet 保留草稿、驗證與版本。Worker 可提出草稿、請求驗證，QA 以自身角色確認並發佈同一個已通過驗證的 revision。草稿修改後須重新驗證 |

Whippet 已有依 Test 建立正式 Run、讀 Run 與附件、驗證草稿及發佈的能力。現有正式 Run 使用排程當時的已發佈版本。整合重測須在排程交易中鎖定要求的已發佈版本，或在不同版本已發佈時拒絕請求。整合前須驗證服務認證、冪等請求鍵及執行與實際環境／部署版本的綁定。執行接收端無法穩定查證這些資料時，結果只供人工參考。 [現況盤點](../research/baseline.md)

## 去重、重測與狀態一致性

- **工作索引。** 一張單同一有效輸入版本只啟動一個分流工作。收到新客戶回覆時撤銷先前工作的對外寫入資格，依新版本建立工作。PM／RD 工作在 D1 記錄領件、待客戶補資料、待團隊審查、待 MR 審查、待部署、待重測、待客戶確認、阻塞或完成及其續辦條件。回饋單在對外留言或請確認後可進 `needs_input`，客戶結案後才進 `completed`。
- **巡檢失敗群組。** 使用 `(project_slug, environment, workspace_id, test_id, check_key, failure_signature)`。簽章取自有界、脫敏、版本化的規則，例如失敗斷言 ID 及類型，排除時間、隨機 ID 與客戶值。獨立保存 Run ID 與處理收據，讓事件重送不重複累計；同群組的新 Run 追加失敗次數與最後發生時間。測試發新版本後仍可辨識同一問題，但重測須核對實際版本。
- **發單競態。** 接收端以仍開啟的失敗群組唯一約束及單一資料庫交易建立回饋單與來源對應，並保存反向連結待送紀錄。未結的群組繼續併入同張單。結案後新確認的復發可建立另一張單並連回前次。舊 Run、遲到事件與既有重測重播不能建立新復發。Whippet 寫回失敗時重送同一個關聯，保留已建立的工單。
- **重測關聯。** 對同一 `(project_slug, environment, deployment_id, test_id, version_id)` 建立一次正式 Run，將受影響的單關聯到該 Run。修復 MR 的 commit 必須由部署的 commit／建置清單證實已上線；純巡檢可使用預先核准的部署與測試對應。Run 須覆蓋原失敗檢查，且實際執行於相同環境與指定版本。部署版本不可查證、檢查跳過、Runner 失聯、超時或取消時，回報待查並保留工單。
- **結果套用。** 最新適用部署的重測通過、證據齊全且沒有更新的失敗時，巡檢工作可標為已驗證。重測失敗更新原單及受影響工作，變更的失敗簽章留在原重測紀錄供團隊判斷。後到的舊成功、歧異的結果與已失效的客戶回覆不能覆蓋較新狀態。啟用巡檢自動結案的專案仍須逐單核對純巡檢來源和全程團隊限定；有客戶參與的單僅可請客戶確認。

## 失敗復原與資料保護

- **持久處理。** Airedale 在 D1 提交工作或明確的忽略原因後回覆已接收。Worker 收妥一批回覆才保存整合游標，並支援重疊補讀及回放。工作使用租約、心跳與單調遞增的所有權代次。D1 拒絕逾期租約更動工作與回饋單。人工接手時停止該單的自動寫入，並確認進行中外部操作的結果。
- **操作收據。** 外部寫入前在 D1 記錄操作意圖，驗證租約後由 Worker 執行，成功後提交權威結果。相同操作 ID 與相同負載回傳原結果；相同 ID 且負載不同回報衝突。若結果不明，先讀取權威物件並透過操作 ID 或唯一外部參照核對。接收端若無冪等操作或可查證結果的支援，狀態轉待人工確認，避免盲重送留言、MR、Run 或結案。
- **重試。** 網路中斷、暫時性服務錯誤及限流使用有上限的退避與擾動，並遵守 `Retry-After`。權限錯誤、無效資料或版本衝突進入相應的阻塞／重新評估流程。達重試上限後保留原因、當前步驟、修復方式與操作鍵，讓團隊可從失敗點恢復。
- **服務身分。** PM、RD、巡檢橋接、部署事件和 Whippet 各自授權，可單獨撤銷及輪替。服務憑證從部署環境注入。Git 只允許核准的工作分支、核准 remote 與 MR 建立權。模型的輸出不能自行授權發佈、合併、部署或擴大執行範圍。
- **資料最小化。** 回饋單、附件、ELK、測試腳本及模型輸出均視為不受信任。Worker 只提供必要且已遮罩的片段。團隊原始證據留在內網受保護位置，D1 保存工作狀態、稽核所需的 actor、scope、correlation ID、時間、結果及授權參照。客戶留言只使用白話摘要與安全的操作建議。
