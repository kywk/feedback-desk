# 回饋處理與巡檢自動化需求

## 目標與範圍

客戶可繼續在 Airedale 提交回饋、補資料及確認修復。內網 Worker 以專案設定內的程式庫、文件及 ELK 證據協助 PM／RD 分流。Whippet 例行巡檢發現問題時建立團隊回饋單，部署後重跑對應測試，讓團隊能追到從失敗、修正到驗證的完整結果。系統責任、事件格式、授權及重試規則見 [整合契約](../architecture/integration.md)。

| 角色 | 主要操作 |
| --- | --- |
| 客戶 | 開單、補資料、讀取白話回覆、確認完成 |
| PM Agent | 取單、認領、委派 RD、分流、回覆與交接、彙整待辦 |
| RD Agent | 查閱專案範圍內的資料、判斷根因與需求、提出方案、依門檻修正並發 MR |
| 團隊 | 審查待決事項與 MR，沿用專案現有審查、合併及部署流程，可接手或停用自動化 |
| QA | 在 Whippet 查看測試草稿及驗證證據，確認正式發佈 |

## 回饋分流

1. PM 收到新單或新客戶回覆後，檢查專案範圍和處理版本，再認領並派 RD。若尚無可回答的具體事實，先整理目前已知資訊與需要確認的問題。
2. RD 依範圍查閱程式庫與業務說明。需要日誌時，按專案、服務、環境、發生時段等條件查詢 ELK，用已遮罩的參照保留證據。精準說明證據能支持的判斷與仍需釐清的項目。
3. PM 依 RD 的結論分流，把等待對象、理由和下一步放入團隊交接。釋放認領後，待客戶、待審查及阻塞工作以明確的狀態和恢復條件管理。

| 分流 | 判斷與輸出 |
| --- | --- |
| 說明 | 證據支持預期行為或操作方式時，以客戶聽得懂的文字自動回覆，說明原因及能採取的操作。等待客戶回覆或確認 |
| 補資料 | 問清楚最少必要的缺項，例如頁面、操作步驟、發生時間及已遮罩的錯誤訊息。自動送出後轉等客戶，新回覆到達才重新分析 |
| Bug | 有預期行為與實際結果的差異及可查證證據時，依自評決定修正或送團隊判斷 |
| 需求異動 | 先列出現行行為、預期成果、影響範圍及驗收條件。條件明確的需求異動依同一自評規則處理。涉及取捨或驗收條件待定時，向對應的決策者提問 |

對外文字須通過內容檢查才可自動送出。需要人工判讀的內容進待審草稿，敏感值使用遮罩或省略。PM 回報等待客戶補資料、待團隊決策、待 MR 審查、待部署、待重測與阻塞工作。交接含已做事項、證據索引和下一步，對客戶提供當下確實可做的操作。

## 方案自評與修正

自評是對修正或需求實作的把握度，五項分別給 0–2 分，總分 0–10。RD 必須逐項附理由與證據。0 分表示未知或缺乏依據，1 分表示已有依據且仍有關鍵疑點，2 分表示有可查驗證據。

1. 問題原因或業務需求已釐清。
2. 實作方式與預期行為能具體說明。
3. 影響範圍、相依元件與副作用已核對。
4. 目標程式庫、環境及驗證方法已確認。
5. 驗證證據足以支持下一步，並指出仍須在 CI 或部署後完成的檢查。

| 分數 | 可執行的動作 | 交接條件 |
| --- | --- | --- |
| 8–10 | 在隔離工作目錄從核准基底開分支，修正、執行必要檢查，通過後 commit、push 工作分支並建立 MR | 留下 MR ID／連結、commit、實際驗證結果。MR 建立後等待既有審查與部署流程 |
| 5–7 | 提交內部方案、待決事項與版本，等待團隊審查 | 核准同一版方案可續辦修正；資料、範圍或方案變動後須重新審查 |
| 0–4 | 記錄阻塞原因、證據缺口、可行的補救方式與等待對象 | 進阻塞。取得新證據或權限補正後重新評分，團隊也可接手 |

專案範圍、寫入許可、核准的基底／remote、必要的本地驗證及明確驗收條件是 MR 路徑的必要條件。高分或團隊核准後仍須逐一核對。檢查失敗或 MR 建立結果不可查證時保留工作分支與實際完成步驟，排入阻塞或待確認。推送成功且未建立 MR 只算完成推送。已開 MR 進入既有審查及部署，修正已在目標環境上線且驗證通過後才可請客戶確認。

## 巡檢、部署與重測

1. **巡檢失敗。** 只接受專案啟用且可查證的 Whippet 正式巡檢結果。產品檢查失敗時，將脫敏摘要、測試／Run、時段和證據索引寫入團隊限定巡檢單。同環境、同測試檢查及同類失敗的後續 Run 併入同單，Whippet 的相關 Run 顯示對應工單連結。Runner／環境問題進維運待查。
2. **待部署。** 追蹤 MR 和部署版本。現有流程提供成功部署且能查證實際環境及版本後，Worker 排入相符的 Whippet 正式重測。純巡檢可從專案事先核准的部署／測試對應觸發，受部署影響的單共用同一次測試。
3. **重測成功。** 核對實際執行的環境、版本、部署和檢查覆蓋，並確認未被更晚的失敗或部署取代。客戶單由 PM 請客戶確認，客戶按「通過」或「完成」後結案。純巡檢單留下驗證證據；專案開啟自動結案時才由專用操作更新單據。自動發單預設團隊限定，曾對客戶開放的單或與客戶單的關聯不能使客戶單自動結案。
4. **重測失敗或缺證據。** 更新相關巡檢單並保留待處理工作。部署失敗、缺乏部署版本、測試遭跳過、取消、超時或執行環境錯誤時都保留待查原因。沒有對應的正式測試時列為待補測試或人工提供可查驗的結果。
5. **新增或調整測試。** Worker 可在 Whippet 提出測試草稿並安排驗證。QA 查看驗證結果與證據，確認同一個 revision 才發佈。變更後重新驗證，後續正式執行固定到已發佈版本。

## 驗收條件

| 編號 | 情境 | 可查驗結果 |
| --- | --- | --- |
| A1 | 客戶新單、重複交付與後續回覆 | 同一單據輸入只建立一份工作。客戶補件建立新工作，舊工作無法發出先前的回覆 |
| A2 | 使用說明、缺資料、Bug、已明定驗收的需求異動及業務待決 | 說明與補件以白話送出；補件後待客戶。後三種進入對應評分或待決流程，保留理由與證據 |
| A3 | 注入 8、7、5、4 分，模擬檢查、push 或 MR 失敗，並核准中分方案與補正低分個案 | 8 分且符合必要條件發出可查驗 MR，7／5 分先保存方案，核准同一版本後續辦，陳舊核准遭拒。4 分進阻塞且補正後重評。失敗個案如實留下分支及進度，不能進入待客戶驗收 |
| A4 | 工單要求跨專案查 Git／ELK、操作未核准 remote 或讀取祕密 | 入口以專案範圍拒絕並留下稽核紀錄。客戶與外部模型僅取得需用且已清理的內容 |
| A5 | 重送同一 Whippet Run 結果、兩個 Run 同時回報同類失敗、不同環境發生相同錯誤 | 事件重送維持原收據，兩個 Run 併入一張團隊限定單並記兩次失敗，Whippet 的兩個 Run 都可連回同張單。不同環境分別處理 |
| A6 | 草稿驗證失敗、Runner 中斷或正式巡檢成功 | 驗證失敗保留草稿，Runner 中斷進維運待查，正式巡檢成功記錄執行結果。三者均維持既有產品問題單數量 |
| A7 | MR 已開、部署失敗、不可查證的部署、成功部署、部署事件重送及排測期間測試改版 | 只在實際部署證據符合後觸發一次重測。可由重測 Run 回查部署版本、測試版本及相關回饋單。版本漂移時排測鎖定核准版本或拒絕並重新評估 |
| A8 | 正確的重測通過、較舊的成功晚到、重新部署或新版測試仍失敗 | 只有符合最新部署且覆蓋問題的證據可推進完成。重測失敗維持未結；晚到的成功保留歷史 |
| A9 | 重測成功後處理客戶單、曾分享給客戶的巡檢單、未啟用自動結案的巡檢單及已啟用的純巡檢單 | 客戶單進等客戶並等客戶確認；未啟用或曾分享的巡檢單保留團隊待辦；符合資格的純巡檢單寫入系統結案紀錄 |
| A10 | 嘗試以整合服務帳號發佈測試，或 QA 發佈過期／未驗證 revision | 整合身分無發佈權限，過期或未通過驗證的 revision 遭拒。QA 確認通過驗證的最新 revision 後成功發佈 |
| A11 | Worker 在領件後中斷、服務提交後回覆遺失、限流、人工接手 | 工作可接續，既有工單、留言、MR 和 Run 不因重送重複建立。限流遵守退避，人工接手後過期執行者不能寫入 |
| A12 | 客戶嘗試讀取巡檢單、內部交接、草稿附件或原始測試證據，並檢查稽核 | 客戶只能看到獲授權的單與已送出的客戶內容。團隊可用關聯 ID 查詢來源、驗證、審查、外部寫入和重試結果 |
