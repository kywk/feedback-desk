# W2 分析分流與真實 MR

## 派工共用契約

W2 沿用 W1 的專案與環境前綴、Bearer 身分、工作租約及設定版本。一般客戶從既有入口開單、補件與確認。以下欄位供三個開發任務與 QA 共用。

| 接口 | 誰提供、誰使用 | 輸入與回傳 |
| --- | --- | --- |
| `POST /input` | W2-03 提供，W2-01 使用 | 送目前租約；回 `work`、`report`、選擇性的 `repair_authorization`。`work` 含 `input_revision` 與 `next_action`（`analyze` 或 `repair`）。同一租約只能讀該張工單。 |
| `POST /decisions` | W2-03 提供，W2-01 使用 | 租約、`input_revision`、`operation_id`、`correlation_id`、`analysis`。服務端重算分數、核對政策與授權，在同一交易保存處置、進度、草稿或已發布留言與收據，回 `{receipt}`。 |
| 個人團隊決策與補證 | W2-03 提供 | 團隊在可存取的專案內查閱方案、核准或要求重評。操作綁定服務端產生的方案版本、內容摘要、工單輸入版本、範圍版本與審查者。低分案件補證後重新分析。 |
| 修復作業 | W2-02 提供，W2-01 呼叫 | 從已驗證的 `repair_authorization`、受管 repo 設定與本次租約取得授權。修復內容、基底、檢查與目標分支都受核准方案及範圍限制。外部寫入前記意圖。 |
| `POST /mr-links` | W2-03 提供，W2-02 的可信轉接器產生證據 | 核對同版授權、外部操作與 GitLab 回查的專案、MR ID/IID、URL、來源分支、目標分支及 head SHA，保存關聯與收據，釋放租約。MR 建立後等待審查。 |

`analysis` 包含 `classification`（`explanation`、`needs_information`、`bug`、`change_request`）、`summary`、`impact`、`criteria`、`evidence_refs`、`missing_requirements`、`assessment`，依分流另附 `proposal` 或 `customer_body`。五項評分依需求中的順序，每項包含 0～2 整數、理由與可回查的證據參照。評分規則、欄位約束及樣本由同份共用契約匯出，內網與 DMZ 使用同一份。

可修 Bug 與驗收明確的異動依總分分流。8～10 分具備可查證依據且範圍核准時進入修復。5～7 分待團隊核准同版方案。0～4 分留下缺口、等待對象及恢復條件。操作說明與補件問句須通過政策及去敏檢查才能發送。待決業務取捨交由團隊處置。

每個操作鍵綁定穩定的語意內容。相同操作回傳既有收據，內容不一致回 409。輸入已變或人工接手後禁止新的舊版寫入。客戶單維持既有結案流程。真實 MR 驗收保存 GitLab 回查結果，測試替身另列。[GitLab MR API](https://docs.gitlab.com/api/merge_requests/)
