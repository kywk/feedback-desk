起點為 Feedback Desk `de632ed`、Whippet `1062da1`。W2-04 的本機 GitLab MR 已在兩張獨立工單通過驗收。本批已啟動兩個開發端的唯讀介面盤點；產品實作與跨服務驗收待進行。

| 任務 | 依賴與負責範圍 | 實作前需固定的契約 |
| --- | --- | --- |
| W3-01／04 | Feedback Desk 與內網 consumer，依 W1 工作佇列及巡檢事件契約 | W1 的領件、有效租約及團隊審查依賴 customer_ingress。每個專案只能有一個啟用的客戶入口。巡檢要按專案與環境另行授權，再以獨立的轉接身分送件。 |

| W3-03 | QA，依前三項的共用契約 | 同群組不同 Run 各計一次；回應遺失重送仍回原收據；跨環境分開。區分正式巡檢斷言失敗、草稿驗證與 Runner 中斷。 |

依 [Wave 計畫](../waves.md) 分別實作 DMZ 收件、Whippet 終態與關聯、內網轉接及測試準備。驗收須從兩個真實失敗的 Whippet Run 查回同一張工單。

Whippet 的 queue_seq 是入隊順序，晚完成的舊 Run 可能落在已讀位置之前。輪詢應依終態提交順序，或用時間與 Run ID 重疊讀取並持久化收據。建單前須核對同一 attempt 的已保存證據；未知失敗或缺少用途的舊 Run 留待判讀。工單 URL 由核准來源與 public_id 組成。既有發布仍由 QA 走 revision、validation 與 summary 守衛。

### 本機驗收環境

Whippet Web `http://127.0.0.1:19830`、API `http://127.0.0.1:19831`、合成網站 19832、Feedback Desk `http://127.0.0.1:19833/p/w3-demo`。同一支已發布的 Playwright 測試會開啟合成網站，檢查標題是否為 Ready。測試以 SQL 準備已發布版本與 Workspace，執行走正式排程、派送、瀏覽器、報告與橋接 API。作者與 QA 發布守衛另用真 PostgreSQL、HTTP 及合成驗證／摘要測資驗收。

Docker 使用專用 Compose 專案 `fd-w3-qa`、`fd-w3-qa-runner` 與合成站台容器 `fd-w3-qa-target`。最終資料庫為 `fd_w3_final`，配對 `.feedback-desk/w3/work-final` 的 Manager journal。首次換庫沿用舊 journal，Server 拒絕不屬於新資料庫的結果；切換配對目錄後派送恢復。第一次試跑的資料庫與 journal 已分開保留。

從 Feedback Desk 根目錄可啟動現有測試容器，並重開同一份本機回饋資料：

```sh
docker start fd-w3-qa-postgres-1 fd-w3-qa-server-1 fd-w3-qa-web-1 fd-w3-qa-target fd-w3-qa-runner-manager-1
npm run build
set -a
. ./.feedback-desk/w3/tokens.env
set +a
W3_D1_PERSIST="$PWD/.feedback-desk/w3/d1" node test/w3/serve.mjs
```

本機資源使用忽略版控的 `.feedback-desk/w3/`，其中 `inspection.json` 保存來源、版本與 token 雜湊，`compose.env` 與 `tokens.env` 以 0600 保存憑證。Whippet 的平台登入使用專用環境內的管理憑證；團隊開啟工單須先登入 Feedback Desk 的 `w3-demo` 專案，本機團隊存取憑證參照為 `W3_DESK_OWNER`。正式部署與內網輪詢另見[橋接器操作說明](../../../scripts/agents/inspection/README.md)。
