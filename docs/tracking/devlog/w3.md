# W3 第一批契約盤點

起點為 Feedback Desk `de632ed`、Whippet `1062da1`。W2-04 的本機 GitLab MR 已在兩張獨立工單通過驗收。本批已啟動兩個開發端的唯讀介面盤點；產品實作與跨服務驗收待進行。

| 任務 | 依賴與負責範圍 | 實作前需固定的契約 |
| --- | --- | --- |
| W3-01／04 | Feedback Desk 與內網 consumer，依 W1 工作佇列及巡檢事件契約 | W1 的領件、有效租約及團隊審查依賴 customer_ingress。每個專案只能有一個啟用的客戶入口。巡檢要按專案與環境另行授權，再以獨立的轉接身分送件。 |
| W3-02 | Whippet server 與 Run 詳情，依既有終態及證據 | run-activity 依排隊次序列出；Run 詳情有版本與終態，attempt 尚未對外提供。需有可驗證的巡檢用途、環境、斷言分類、受限機器身分及工單關聯讀寫。 |
| W3-03 | QA，依前三項的共用契約 | 同群組不同 Run 各計一次；回應遺失重送仍回原收據；跨環境分開。區分正式巡檢斷言失敗、草稿驗證與 Runner 中斷。 |

依 [Wave 計畫](../waves.md) 分別實作 DMZ 收件、Whippet 終態與關聯、內網轉接及測試準備。驗收須從兩個真實失敗的 Whippet Run 查回同一張工單。

Whippet 的 queue_seq 是入隊順序，晚完成的舊 Run 可能落在已讀位置之前。輪詢應依終態提交順序，或用時間與 Run ID 重疊讀取並持久化收據。建單前須核對同一 attempt 的已保存證據；未知失敗或缺少用途的舊 Run 留待判讀。工單 URL 由核准來源與 public_id 組成。既有發布仍由 QA 走 revision、validation 與 summary 守衛。
