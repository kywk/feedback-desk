# 回報自動化實作波次

依序交付可靠接單、研判與修復、巡檢建單，以及部署後重測。這份文件是派工與驗收清單，目前各項皆待實作。需求見[回報自動化規格](../requirements/automation.md)，系統邊界與跨服務介面見[整合架構](../architecture/integration.md)。

## 派工與交付

| 角色 | 模型 | 寫入與交付範圍 |
| --- | --- | --- |
| 總指揮 | 依派工環境 | 鎖定共用契約、分派檔案、管理任務提交、執行波次整合與記錄結果 |
| Airedale 開發 | Codex `gpt-6.2-sol` / `xhigh` / `fast` | DMZ 的工單、來源事件、工作佇列、操作收據、D1 migration、整合 API 與相關單元測試 |
| 內網 Worker 開發 | Codex `gpt-6.2-sol` / `xhigh` / `fast` | 專案設定與執行隔離、佇列消費、分析分流、GitLab MR、巡檢及部署事件接線 |
| Whippet 開發 | Codex `gpt-6.2-sol` / `xhigh` / `fast` | Whippet 的巡檢結果、工單連結、測試草稿與部署後重測入口，遵守 Whippet 專案規範 |
| QA | Codex `gpt-6.1-terra` / `high` / `fast` | 整合測試、測試資料與驗收證據。產品缺陷交回對應的開發 owner |

- 同批工作可以並行。總指揮先鎖定該批共用欄位、狀態與錯誤語意，各 owner 在獨立檔案及測試資料上工作。若必須修改共用檔案，由總指揮指派一人寫入，另一方以契約 fixture 開發。
- 每個 task 跑過必要單元測試與相關型別檢查後，依各 repo 規範產生獨立 commit。交接記錄 task ID、commit、實際執行的檢查與結果。跨 repo task 各自提交並記下對應版本。
- 每個 wave 收尾跑 Airedale `npm run typecheck` 與 `npm test`、受影響的內網 Worker 及 Whippet 服務完整測試，再跑該 wave 的端到端驗收和前波關鍵旅程回歸。Whippet Go 服務在各自模組目錄跑 `go test ./...`，Runtime 有修改時再依該模組執行完整驗證。QA 用隔離資料庫、測試 GitLab repo 與測試部署環境。
- 真實 MR、Whippet Run 與部署由隔離環境的識別碼及實際查詢結果驗收。測試替身可支援元件開發。真實整合未跑通時，保留待驗收狀態並記錄缺少的環境、權限或證據。

## W1 可靠收單與專案隔離

現有 `reports.status` 代表回報單正在等誰。自動化工作的進度、租約、審查與續辦由 Airedale 的 D1 另外保存。既有認領與交接仍供團隊協作，Worker 取得有效租約後才執行工作。

| 任務 ID | 工作與所有權 | 依賴 | 單項驗收 |
| --- | --- | --- | --- |
| W1-01 | Airedale。以 D1 寫入可補讀的工單事件與持久工作佇列。新增專案限定的領件、續租、到期接手與受限回寫 API。核對工單版本與租約代次，保存外部操作意圖及冪等收據。 | W1 契約 | 同一工單輸入版本只有一筆工作，兩個 Worker 同時取件只有一個取得有效租約。相同操作 ID 重送取得原結果，內容改變時回衝突。工單版本已改、租約失效或人工接手後，舊操作被拒。 |
| W1-02 | 內網 Worker／專案隔離。以 project slug 與環境選擇設定，載入 repo、remote、基準分支、本機說明、ELK 索引／欄位／查詢範本與驗證權限。保存設定版本，工具層強制範圍。 | W1 契約 | A 專案的工作無法開啟 B 專案 repo 或查詢 B 索引。未核准 remote、未知設定、路徑或符號連結跳脫與未允許的查詢遭拒。工單內指令無法改寫工具範圍或取得機密。 |
| W1-03 | 內網 Worker／接單。輪詢可領工作，取得租約後執行，續租並保存進度。支援游標補讀、失敗重試與退避，切換同專案的舊輪詢入口。 | W1-01、W1-02 | 重啟後可接續已保存階段，重送不多建工作。待審或阻塞的工作即使工單仍為 `new` 也不重派。舊單依啟用規則接手，已人工接手的單不被自動強制取得。 |
| W1-04 | QA。準備跨專案 fixture，以及斷線、租約逾期、ACK 遺失與重送腳本。 | 可依 W1 契約先寫，驗收依賴 W1-01～03 | 每個案例能比對工作紀錄、開始次數、執行個體與退避狀態，並驗證客戶端看不到內部執行細節。 |

**派工批次**　W1-01、W1-02 與 W1-04 測試準備並行 → W1-03 接線 → W1-04 整合。

**整合驗收**　從一般客戶入口建立 A 專案回報，再由客戶補件。確認同版只派發一次，新回覆送入新版工作，舊工作失去寫入權。重啟、限流及人工接手後狀態可追查，並以 B 專案的 repo、ELK 和工單做反向測試。

**需求驗收**　A1、A4、A11 的接單與回寫復原，以及 A12 的工單與內部紀錄隔離。

## W2 分析分流與真實 MR

分析只使用專案核准的 repo、ELK 與必要證據。輸出包含問題類型、根因依據、影響、修改方案、驗證方式、五項自評的分數與理由，以及缺少的資訊。操作詢問與補資料走經檢查的白話回覆。Bug 與驗收明確的需求異動再按分數及證據分流，待決事項交給對應的決策者。

| 任務 ID | 工作與所有權 | 依賴 | 單項驗收 |
| --- | --- | --- | --- |
| W2-01 | 內網 Worker／分析。實作 PM／RD 的唯讀研判、結構化驗證、說明／補件／Bug／需求分流及待辦恢復。8–10 依門檻修復，5–7 交團隊審核，0–4 記錄阻塞與所需資料。 | W1、W2 契約 | 覆蓋 0、4、5、7、8、10 和不合法分數。高分缺證據時停止自動修復。中分核准綁定工單輸入、方案與專案範圍版本，條件改變就重審。低分須在新證據到達、權限補正或團隊處置後重評。補件送出後等新客戶輸入。 |
| W2-02 | 內網 Worker／修復。依核准 repo、基準分支建獨立工作樹。符合高分門檻或同版中分方案已獲核准，才實修並跑必要測試、推送工作分支，以及用 GitLab API 建立或查回 MR。每項外部寫入前核對租約並保存操作意圖。 | W1-02、W2-01 的修復輸入契約，可用 fixture 並行 | 測試通過且 GitLab 可查到 MR ID、URL、來源及目標分支，才記錄 MR 已建立。測試或推送失敗留內部紀錄。建 MR 回應遺失後對帳取得同一張 MR。 |
| W2-03 | Airedale。整合客戶回覆、團隊待審草稿、交接、審查決定及 MR 關聯。操作說明與補件問句通過專案政策和內容檢查才可自動送出。 | W1-01、W2 結果契約，可用 fixture 並行 | 自動回覆只出現一次，補件留言使單進等客戶。收到補件後舊版本的待發留言遭拒。待審及阻塞原因只給團隊讀取，同版核准才可恢復工作。MR 建立或合併時仍等待可信部署與重測證據。 |
| W2-04 | QA。準備操作詢問、缺資料再補件、可修 Bug、明確需求異動、需人工判斷與缺證據的案例。 | 可依 W2 契約先準備，驗收依賴 W2-01～03 | 核對白話回覆、補件往返、待審核准同版續辦、低分解除後重評及真 MR。建立 MR 的提示網址、空 diff、測試失敗與遠端逾時無法冒充成果。 |

**派工批次**　W2-01、W2-02、W2-03 與 W2-04 測試準備按已鎖契約並行 → W2-04 跑三條分流旅程。

**整合驗收**　從客戶入口重放操作說明與補件往返，確認去敏的白話回覆及新版重分析。測試 8–10 的可驗證問題在核准 repo 開出真實 MR，重試後仍只有一張。5–7 的方案先暫停，舊版核准遭拒，同版獲核准後才續辦。0–4 先顯示證據缺口，條件解除後重新評分。團隊可追到決策、驗證和外部操作，客戶端只見已發布內容。

**需求驗收**　A2、A3，以及 A1 的補件重入、A11 的留言與 MR 重送、A12 的分流決策稽核。

## W3 Whippet 巡檢失敗建單

Whippet 擁有巡檢 Run 與測試證據，並在 Run 頁回顯工單連結。Airedale 擁有工單與關聯紀錄。第一版由內網 Worker 拉取 Whippet 結果，再向 DMZ 的 Airedale 受限端點送出 `POST` 並將關聯回寫 Whippet。

| 任務 ID | 工作與所有權 | 依賴 | 單項驗收 |
| --- | --- | --- | --- |
| W3-01 | Airedale。接收已查證的巡檢失敗事件，依專案、環境、workspace、測試、檢查與失敗簽章聚合到未結團隊單，再接到 W1 的工作入口。 | W1-01、W3 契約 | 重送與回應遺失回到同一 `public_id`。同群組不同 Run 各計一次，並行回送只建立一張單。不同環境分開，未授權來源遭拒。結案後新確認的復發保留與原案的關聯。 |
| W3-02 | Whippet。提供供內網 Worker 拉取的可查驗終態與已保存報告，接收工單關聯並在 Run 頁顯示對應的 Airedale 連結。沿用測試草稿、revision 驗證與發佈流程。 | W3 契約，可用 fixture 與 W3-01 並行 | Run 回傳 workspace、Run、attempt、測試版本、環境與受權限保護的證據連結。獲授權的使用者能從相同群組的各 Run 開到同一張工單。整合身分可提草稿及請求驗證，發佈依 QA 權限與 revision 守衛。 |
| W3-03 | QA。準備能通過、能重現斷言失敗、Runner 中斷的巡檢，以及同類失敗在不同環境的 Run。驗證有接入測試作者流程時的草稿與發佈。 | 可先準備，驗收依賴 W3-01、W3-02、W3-04 | 同群組的兩個 Run 可追到同單，重送不加次數，跨環境分開。整合帳號無法發佈，未驗證或過期的 revision 被拒，QA 可確認並發佈最新通過驗證的 revision。 |
| W3-04 | 內網 Worker／巡檢轉接。輪詢 Whippet 終態並回查 Run，以專用身分 `POST` 至 DMZ 建單入口，再將工單對應回寫 Whippet。需要補測試時提出草稿並請求驗證。 | W1-03、W3 契約，可先用 fixture 開發 | 重送與人工重放保留來源 ID 及原收據，兩端的關聯可補寫。正式巡檢成功、Runner 問題與草稿驗證失敗各自留下結果或待查原因，無產品缺陷單。 |

**派工批次**　W3-01、W3-02、W3-04 的契約實作與 W3-03 測試準備並行 → W3-04 接線 → W3-03 實跑整合。

**整合驗收**　在同環境跑兩次實際的 Whippet 斷言失敗，兩個 Run 的連結都指向同一張團隊單，各自的失敗與證據各計一次。併發、回應遺失與重送維持原收據。不同環境另行處理，通過、草稿驗證失敗、取消與 Runner 問題不觸發產品修復。有接入測試作者流程時，從整合身分提草稿和安排驗證，驗證後修改草稿，實測舊版或未驗證 revision 拒絕發佈，最後由 QA 確認最新通過的 revision 並發佈。任一服務暫停，另一服務的既有入口仍可使用。

**需求驗收**　A5、A6、A10，以及 A11 的開單重送、A12 的巡檢單與測試證據隔離。

## W4 部署後重測閉環

可信 CI/CD 成功部署事件才排重測。重測使用工單關聯的 Whippet 測試、已發佈版本與目標環境，結果必須能追到實際部署的版本。

| 任務 ID | 工作與所有權 | 依賴 | 單項驗收 |
| --- | --- | --- | --- |
| W4-01 | 內網 Worker／部署接線。接收可信部署事件並比對已知工單、MR、commit 與環境，保存部署與重測的關聯。 | W2-02、W2-03、W3、W4 契約 | 單純 MR 合併、錯誤環境、無法驗證版本及部署失敗不排重測。有效事件重送只會關聯同一筆重測請求，較舊部署不覆蓋較新部署。 |
| W4-02 | Whippet。用固定的已發佈測試版本建立重測 Run，受同一部署與測試影響的工單共用 Run，透過既有執行與終態機制回傳結果。 | W3-02、W4 重測契約，可用 fixture 並行 | 相同專案、環境、部署、測試及版本只排一個 Run。Run 證據綁定部署、環境、版本與 attempt。產品斷言失敗、逾時、取消與環境錯誤可分辨，舊 attempt 無法覆蓋目前結果。 |
| W4-03 | Airedale。依授權來源與關聯接受重測結果。通過才依規格產生驗收回覆或完成合資格的內部巡檢單，原問題的重測失敗把證據留在原單。 | W3-01、W4 結果契約，可用 fixture 並行 | 重複通過結果只生效一次。舊部署或環境、測試版本不符時停在待處理。同群組重測失敗不重複開單。客戶單由既有「完成」或「通過」入口結案。純巡檢單僅在專案啟用且符合全程團隊可見與其他結案條件時，由專用入口結案。 |
| W4-04 | QA。準備可部署測試環境、正反兩條版本旅程與事件重送、亂序測試。 | 可先準備，驗收依賴 W4-01～03 | 覆蓋真正部署後通過、仍然失敗、環境錯誤、舊結果晚到、不同環境與相同事件重送。 |

**派工批次**　W4-01、W4-02、W4-03 與 W4-04 測試準備按已鎖契約並行 → W4-04 跑整條閉環。

**整合驗收**　跑完「Whippet 失敗 → Airedale 建單 → 內網 Worker 研判與修復 → GitLab 真實 MR → 測試環境部署 → Whippet 重測 → 回寫」。保存各站的 ID 與結果。通過後分別驗證客戶單請客戶確認、未啟用自動結案的巡檢單留團隊待辦、合資格的純巡檢單寫入系統結案。用另一個部署重測失敗並晚送前一版的通過結果，確認維持未通過且同一張單可繼續處理。最後重跑 W1–W3 的關鍵旅程與受影響服務的完整測試。

**需求驗收**　A7、A8、A9，以及 A11 的 Run 與回寫復原、A12 的部署和重測稽核。
